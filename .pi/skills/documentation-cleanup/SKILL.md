# Documentation cleanup

Review documentation as user-facing product material, not as an isolated copy-editing exercise. Preserve behavior and terminology unless the implementation shows that the documentation is wrong.

## Workflow

1. Read the repository instructions and check the working tree before editing.
2. Find the relevant documentation, including `README.md`, crate-level `//!` comments, public-item `///` comments, examples, and release notes when applicable.
3. Inspect the implementation, tests, and package metadata needed to verify every behavioral, versioning, feature, and API claim.
4. Review the documentation as a whole before making local edits. Look for duplication, omissions, stale terminology, inconsistent syntax, and sections that are in the wrong order.
5. Make focused edits that improve scanability without removing important caveats.
6. Validate formatting, examples, links, and documentation builds.

## Editing principles

- Lead with what the crate or API does, followed by its scope and important non-goals.
- Prefer short sections, descriptive headings, direct sentences, tables for compact attribute or option references, and examples for workflows.
- Introduce the common path before advanced behavior and limitations.
- Keep names, attribute syntax, method signatures, dependency versions, feature names, generated SQL, trait bounds, and error behavior consistent with the code.
- Show complete attribute syntax such as `#[rusqlite(option)]` in references rather than switching between full and abbreviated forms without explanation.
- Explain interactions and precedence between options explicitly.
- Distinguish compile-time validation from database behavior that can only fail at runtime.
- Keep security warnings near the API that creates the risk and state both what is safe and what callers should do instead.
- Avoid repeating the same detail in many places. Keep the README task-oriented, crate documentation concise, and item documentation specific to the item.
- Preserve useful edge cases and limitations, but rewrite dense caveats into shorter paragraphs or lists where appropriate.
- Do not add marketing language, unsupported guarantees, or implementation details that users do not need.

## Rust and Markdown examples

- In a README, optimize code blocks for rendered Markdown. Do not use rustdoc's hidden-line `#` convention there; GitHub displays those markers literally.
- In Rust doc comments, hidden doctest setup lines are acceptable when they keep the rendered example focused.
- Prefer examples that compile and use the public import path users should actually choose.
- Keep SQL examples aligned with the exact statements generated by the implementation.
- Use proper typographic punctuation in prose where it improves readability, but retain ASCII syntax in code.
- Follow repository wrapping rules. In this repository, do not hard-wrap Markdown prose; let rendered views wrap it. Rust documentation comments must remain formatted with `cargo fmt`.

## Validation

Run the checks appropriate to the repository. For this Rust workspace, use:

```bash
cargo fmt --all -- --check
git diff --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
```

If a check is unavailable or fails for reasons unrelated to the edits, report that clearly. Review the final diff for accidental behavior changes, malformed Markdown tables, visible doctest scaffolding in README files, and unnecessary churn.
